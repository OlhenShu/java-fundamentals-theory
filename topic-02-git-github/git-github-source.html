    0Цілі теми

    Після цієї теми ви зможете пояснити, навіщо команді система контролю версій і чим Git відрізняється від звичайного копіювання тек. Ви налаштуєте Git поточної версії, створите репозиторій і впевнено проведете зміну через три стани — робочу теку, staging area і коміт, — читаючи вивід git status, git diff і git log. Ви складете .gitignore, безпечно скасуєте зміни командою git restore і працюватимете в гілках через git switch, зливатимете їх і розв’язуватимете простий конфлікт. І нарешті, ви підключите репозиторій GitHub, надсилатимете й отримуватимете зміни та пройдете повний цикл Pull Request.

    1Навіщо системи контролю версій

    Проблема. Без спеціального інструмента історію проєкту ведуть копіюванням: project_final, project_final_2, project_final_real. Такий підхід швидко ламається. Незрозуміло, чим одна копія відрізняється від іншої, легко перезаписати не ту теку, а коли над кодом працюють двоє, хтось неминуче затре чужі зміни.

    Чому так. Система контролю версій (VCS) записує зміни файлів у часі, тож до будь-якої збереженої версії можна повернутися, порівняти версії між собою та побачити, хто і коли змінив конкретний рядок. Ранні системи були централізованими: історія жила на одному сервері, і без зв’язку з ним працювати було неможливо, а збій сервера означав втрату всього. Git — розподілена система: кожен, хто клонує репозиторій, отримує повну копію історії. Тому більшість операцій у Git виконуються локально й миттєво, а кожна копія водночас є резервною.

    Рішення. Git зберігає історію як послідовність знімків (snapshots) усього проєкту: щоразу, коли ви фіксуєте зміни, Git запам’ятовує, як виглядали всі відстежувані файли в цей момент. Незмінені файли він не дублює, а посилається на вже збережену версію. Кожен знімок має унікальний ідентифікатор — хеш, обчислений з його вмісту, — тож непомітно зіпсувати історію неможливо.

    Коли застосовувати. У будь-якому проєкті, де є текстові файли, що змінюються: код, автотести, документація, конфігурації. Навіть працюючи самі, ви отримуєте «машину часу» і можливість безпечно експериментувати.

    Джерело: Pro Git, 1.1 — About Version Control; Pro Git, 1.3 — What is Git?

    2Встановлення і налаштування Git

    Проблема. Кожен коміт у Git підписаний іменем та email автора. Якщо їх не задати, Git або відмовиться створювати коміт, або підставить щось на кшталт імені вашого комп’ютера — і в спільній історії буде незрозуміло, хто що зробив.

    Рішення. Встановіть Git (на Windows — пакет Git for Windows, який містить і термінал Git Bash; на macOS і Linux — через пакетний менеджер) і перевірте версію. Станом на кінець вересня 2026 року актуальна версія — Git 2.55. Потім один раз задайте глобальні налаштування: ім’я, email і назву гілки за замовчуванням.

    Чому саме так. Налаштування Git мають три рівні: системний (--system, для всіх користувачів комп’ютера), глобальний (--global, для вас у всіх репозиторіях) і локальний (без прапорця, лише для поточного репозиторію). Нижчий рівень перекриває вищий, тож у робочому проєкті можна, наприклад, вказати корпоративний email, не чіпаючи особистого. Команда git config --list --show-origin покаже всі налаштування і файл, з якого взято кожне.

    Відмінності між версіями: master чи main

    Git 2.x без налаштування init.defaultBranch досі називає першу гілку master і показує підказку про це, а GitHub створює нові репозиторії з гілкою main. Тому ми одразу задаємо main, щоб локальні й віддалені назви збігалися. У Git 3.0, вихід якого очікують наприкінці 2026 року, main має стати назвою за замовчуванням. Старі туторіали з master не помилкові — це та сама гілка під іншою назвою.

    Порада

    Для GitHub вказуйте той самий email, що й в акаунті GitHub. Тоді сайт пов’яже ваші коміти з профілем.

    Джерело: Pro Git, 1.5 — Installing Git; Pro Git, 1.6 — First-Time Git Setup; git-config — Reference

    3Три стани: робоча тека, staging area, репозиторій

    Проблема. Ви виправили баг і заодно поміняли кілька рядків для налагодження, які в історію потрапити не повинні. Якби Git фіксував одразу все змінене, кожен коміт був би сумішшю потрібного й випадкового.

    Чому так. Тому Git має проміжний крок. Файли проєкту живуть у трьох місцях. Робоча тека (working tree) — це звичайні файли на диску, які ви редагуєте. Staging area, або індекс, — це підготовлений знімок того, що ввійде в наступний коміт. Репозиторій — прихована тека .git, де зберігаються всі зафіксовані знімки. Відповідно, змінений файл буває в стані modified (змінено, але не підготовлено), staged (підготовлено) і committed (збережено в історії).

    Рішення. Типовий цикл виглядає так: ви змінюєте файли в робочій теці, командою git add вибірково переносите потрібні зміни в staging area, а командою git commit фіксуєте підготовлений знімок у репозиторії. Важливо розуміти, що git add копіює в індекс файл у тому вигляді, який він має саме зараз. Якщо після цього ви знову зміните файл, нові правки самі в коміт не потраплять.

    Коли застосовувати. Щоразу, коли робите коміт. Звичка спершу переглядати git status і додавати файли свідомо, а не все підряд, — головний захист від випадкових змін в історії.

    Джерело: Pro Git, 1.3 — What is Git? (The Three States)

    4Перший репозиторій: init, status, add, commit, log, diff

    Створення репозиторію

    Команда git init перетворює звичайну теку на репозиторій: створює в ній приховану теку .git, де житиме вся історія. Файли проєкту при цьому не змінюються і самі по собі ще не відстежуються. Другий спосіб отримати репозиторій — склонувати наявний командою git clone; про це в розділі про віддалені репозиторії.

    Типова помилка

    Виконати git init у домашній теці чи на робочому столі. Чому це погано: Git почне вважати частиною проєкту все, що лежить усередині, — документи, завантаження, інші проєкти. Як уникнути: спершу перейдіть у теку конкретного проєкту і перевірте шлях командою pwd.

    Цикл змін: status → add → commit

    Проблема. Перш ніж щось фіксувати, треба знати, що саме змінилося і що вже підготовлено. Рішення. git status показує стан кожного файлу відносно останнього коміту та індексу. Короткий формат git status -s виводить по рядку на файл із двома символами стану: лівий описує staging area, правий — робочу теку. Символи ?? позначають новий, ще не відстежуваний файл; A — файл, доданий в індекс уперше; M ліворуч — зміна, підготовлена до коміту, M праворуч — зміна, ще не підготовлена. Комбінація MM означає, що частину змін підготовлено, а після git add файл знову редагували.

    Простежте цикл покроково. Команди створення файлів (echo) наведено для Git Bash, Linux і macOS; у реальній роботі ви редагуватимете файли в редакторі.

    Трасування: один файл через три стани

    Підсвічено команду, що щойно виконалася; праворуч — вміст робочої теки, індексу й історії після неї. Хеші комітів у вас будуть іншими: вони залежать від автора і часу.

    Зверніть увагу на два моменти. Після коміту індекс не «порожніє»: він збігається з останнім знімком і далі служить основою для наступного. А останній git status -s показує M, бо рядок Second idea дописали вже після git add, тож у коміт він не потрапив.

    Що покаже git status -s?

    Файл app.txt уже є в останньому коміті з вмістом v1. Запишіть вивід останньої команди.

    Коміт і повідомлення

    git commit -m "Повідомлення" фіксує вміст індексу як новий знімок. Без прапорця -m Git відкриє текстовий редактор для повідомлення. Повідомлення пишуть для людей, які читатимуть історію пізніше: коротко, в наказовому способі, про суть зміни — Add login form, а не fix чи changes. Один коміт має описувати одну логічну зміну, тоді його легко переглянути, а за потреби — скасувати.

    Типова помилка

    Робити git add . не дивлячись. Чому це погано: у коміт потрапляють логи, зібрані файли, локальні налаштування IDE, а іноді й паролі у файлах конфігурації. Як уникнути: перед кожним комітом переглядайте git status, а все, що ніколи не має потрапляти в репозиторій, винесіть у .gitignore.

    Перегляд історії і змін

    Проблема. Через тиждень ви вже не пам’ятаєте, що саме змінювали і що встигли підготувати. Рішення. git log показує історію комітів від найновішого; git log --oneline — по рядку на коміт із коротким хешем, а --format=%s — лише повідомлення. git diff без аргументів порівнює робочу теку з індексом, тобто показує те, що ви ще не підготували. git diff --staged порівнює індекс з останнім комітом — це саме те, що ввійде в наступний коміт. Рядки з + додано, з - видалено.

    Джерело: Pro Git, 2.1 — Getting a Git Repository; Pro Git, 2.2 — Recording Changes to the Repository; Pro Git, 2.3 — Viewing the Commit History; git-status — Short Format; git-diff — Reference

    5.gitignore: що Git має не помічати

    Проблема. У кожному проєкті з’являються файли, які не варто зберігати в історії: результати збирання, логи, залежності, що завантажуються автоматично, локальні налаштування IDE, файли з секретами. Вони засмічують git status, роздувають репозиторій, а секрети в публічному репозиторії — це вже проблема безпеки.

    Чому так. Git за замовчуванням пропонує відстежувати кожен новий файл. Щоб він не помічав певні шляхи, їх описують шаблонами у файлі .gitignore у корені проєкту. Сам .gitignore комітять, щоб правила діяли для всієї команди.

    Рішення. Кожен рядок файлу — окремий шаблон. Рядки з # — коментарі. * відповідає будь-якій послідовності символів, крім /, а ? — одному символу. Шаблон без скісної риски (*.log) діє на будь-якому рівні вкладеності. Скісна риска на початку чи всередині прив’язує шаблон до кореня (/todo.txt — лише файл у корені). Скісна риска в кінці означає «лише теки» (build/). Подвійна зірочка ** охоплює будь-яку кількість тек. Знак оклику на початку повертає раніше проігнорований шлях (!keep.log). Якщо шлях підпадає під кілька шаблонів, перемагає останній.

    Коли застосовувати. Створюйте .gitignore ще до першого коміту. Він не діє на файли, які Git уже відстежує: щоб припинити відстежувати такий файл, його треба прибрати з індексу, і лише тоді правило почне працювати.

    Лабораторія: перевірте свої шаблони

    Змінюйте .gitignore і список файлів — сторінка застосовує ті самі правила, що й git check-ignore. Порівняння регістру літер тут як у Linux: Build і build різні.

      Типова помилка

      Виключити теку і спробувати повернути файл усередині неї: build/, а потім !build/keep.log. Файл залишиться проігнорованим. Чому: якщо проігноровано саму теку, Git узагалі не заходить усередину, тож шаблон для файлу не має на що подіяти. Як уникнути: ігноруйте вміст (build/*), а не теку, і тоді виняток спрацює. Перевірте обидва варіанти в лабораторії.

      Джерело: gitignore — Pattern Format; Pro Git, 2.2 — Recording Changes (Ignoring Files); git-check-ignore — Reference

      6Скасування змін: git restore

      Проблема. Дві найчастіші ситуації: ви додали в індекс файл, який не хотіли комітити, або зіпсували файл і хочете повернути його до останньої збереженої версії.

      Чому так. Історично обидві задачі, а заодно й перемикання гілок, виконувала одна команда git checkout. Через це вона мала дуже різну поведінку залежно від аргументів, і новачки легко втрачали роботу. Тому з’явилися дві спеціалізовані команди: git restore для файлів і git switch для гілок.

      Рішення. git restore --staged <файл> прибирає файл з індексу, повертаючи в індекс версію з останнього коміту. Ваші правки при цьому залишаються в робочій теці. git restore <файл> без прапорців повертає файл у робочій теці до версії з індексу, тобто знищує непідготовлені правки. Підказки про обидві команди Git друкує прямо у виводі git status.

      Важливо

      git restore <файл> — одна з небагатьох команд Git, після яких дані не повернути: правки, яких не було ні в індексі, ні в жодному коміті, Git ніде не зберігав. Перш ніж її виконати, перегляньте git diff <файл> і переконайтеся, що ці зміни справді не потрібні.

      Коли застосовувати. --staged — коли поквапилися з git add; без прапорців — коли хочете відкинути експеримент у файлі.

      Відмінності між версіями

      git restore і git switch з’явилися в Git 2.23. git checkout працює й досі, і ви зустрінете його в старих інструкціях, але в цьому курсі використовуємо нові команди: їхня назва прямо каже, що вони роблять.

      Джерело: Pro Git, 2.4 — Undoing Things; git-restore — Reference

      7Гілки, злиття і конфлікти

      Гілка як вказівник

      Проблема. Ви почали нову функцію, а тут треба терміново виправити баг у робочій версії. Якщо все робиться в одній лінії історії, недороблена функція потрапить у виправлення.

      Чому так. Гілка в Git — це не копія файлів, а лише легкий рухомий вказівник на коміт. Коли ви робите коміт, вказівник поточної гілки пересувається на нього. Особливий вказівник HEAD показує, на якій гілці ви зараз. Тому створити гілку — справа частки секунди, скільки б файлів не було в проєкті.

      Рішення. Для кожної задачі створюють окрему гілку від main: git switch -c feature/search створює гілку і одразу переходить на неї. git switch main повертає на основну гілку й оновлює робочу теку до її знімка. git branch виводить список гілок і позначає поточну зірочкою. Коли задачу завершено, гілку зливають у main командою git merge, а потім видаляють: git branch -d feature/search.

      Типова помилка

      Перемикати гілку з незбереженими змінами. Якщо ці зміни конфліктують із файлами іншої гілки, Git відмовить у перемиканні; якщо ні — правки «переїдуть» разом з вами в іншу гілку, і їх легко закомітити не туди. Як уникнути: перед git switch зробіть коміт або скасуйте зміни, щоб git status був чистим.

      Злиття: fast-forward і merge commit

      Чому буває по-різному. Якщо поки ви працювали в гілці, у main не з’явилося нових комітів, Git просто пересуває вказівник main уперед — це злиття fast-forward, нового коміту не з’являється. Якщо ж історія розійшлася, Git бере спільного предка і верхівки обох гілок, поєднує зміни й створює коміт злиття з двома батьками. За замовчуванням для такого коміту відкривається редактор із повідомленням Merge branch '…'; прапорець --no-edit приймає його без редагування.

      Трасування: гілка, розходження історії, злиття

      До початку в main вже є два коміти. Стан праворуч — вказівники гілок, HEAD, коміти та файли робочої теки. Позначки C1–C5 введено для наочності, Git їх не друкує.

      Що буде виведено?

      У main один коміт Add README. Запишіть вивід останньої команди.

      Конфлікти злиття

      Проблема. Дві гілки змінили той самий рядок того самого файлу по-різному. Git не може сам вирішити, яка версія правильна.

      Чому так. Git автоматично поєднує зміни в різних місцях файлу, але рішення щодо змісту — завжди за людиною. Тому злиття зупиняється, файл позначається як конфліктний (UU у короткому статусі), а в ньому з’являються маркери: між <<<<<<< і ======= — версія поточної гілки (HEAD), між ======= і >>>>>>> — версія гілки, яку зливаєте.

      Що буде у файлі?

      У main файл info.txt містив рядок Opening hours: 9-18. Запишіть вміст info.txt після останньої команди.

      Рішення. Відкрийте файл, залиште правильний варіант (одну з версій, обидві або новий текст) і обов’язково приберіть усі маркери. Потім позначте конфлікт розв’язаним командою git add info.txt і завершіть злиття командою git commit. Якщо хочете повернутися до стану до злиття, виконайте git merge --abort.

      Типова помилка

      Закомітити файл із маркерами <<<<<<< всередині. Git вважає конфлікт розв’язаним у момент git add і не перевіряє, що ви насправді прибрали з файлу. Як уникнути: перед git add знайдіть у файлі пошуком <<< і перегляньте git diff.

      Джерело: Pro Git, 3.1 — Branches in a Nutshell; Pro Git, 3.2 — Basic Branching and Merging; git-switch — Reference; git-merge — How Conflicts Are Presented

      8Віддалені репозиторії і GitHub

      clone, remote, push

      Проблема. Локальний репозиторій бачите лише ви. Щоб працювати в команді й мати копію поза своїм комп’ютером, історію треба десь опублікувати.

      Чому так. Віддалений репозиторій (remote) — це версія проєкту, що лежить деінде, найчастіше на сервісі на кшталт GitHub. Кожен remote має коротке ім’я; той, з якого ви клонували, Git за замовчуванням називає origin. Git також зберігає віддалені гілки на кшталт origin/main — це ваш локальний «зліпок» стану гілки на сервері на момент останньої синхронізації.

      Рішення. Є два шляхи. Якщо проєкт уже на GitHub — git clone <url> створює локальну копію з усією історією і налаштованим origin. Якщо репозиторій створено локально — створіть порожній репозиторій на GitHub, підключіть його командою git remote add origin <url> і надішліть гілку командою git push -u origin main. Прапорець -u запам’ятовує зв’язок локальної main з origin/main, тож надалі достатньо писати просто git push і git pull.

      Важливо: автентифікація

      GitHub не приймає пароль від акаунта для операцій Git через HTTPS. Замість нього використовують personal access token, SSH-ключ або менеджер облікових даних. Git for Windows постачається з Git Credential Manager, який відкриває вхід у браузері під час першого git push.

      fetch і pull

      Проблема. Колега надіслав нові коміти. Як отримати їх, не зламавши власну роботу?

      Чому так і рішення. git fetch лише завантажує нові дані з сервера й оновлює віддалені гілки (origin/main), але не чіпає ваші гілки й робочу теку. Після нього можна спокійно подивитися, що змінилося. git pull — це fetch плюс інтеграція: він одразу вливає origin/main у вашу поточну гілку. git status -sb показує короткий статус разом із порівнянням із віддаленою гілкою: [behind 1] — на сервері є один коміт, якого у вас немає, [ahead 1] — навпаки.

      Коли застосовувати. git pull — на початку роботи і перед git push, щоб мати свіжу версію; git fetch — коли хочете спершу подивитися, що змінилося, нічого не зливаючи.

      Відмінності між версіями

      Якщо історія розійшлася — і у вас, і на сервері є нові коміти, — сучасні версії Git не виконують git pull мовчки, а просять обрати спосіб інтеграції. У цьому курсі обираємо злиття: git config --global pull.rebase false. Тоді git pull створить коміт злиття так само, як git merge.

      Типова помилка

      git push відхилено з повідомленням rejected … (fetch first). Чому: на сервері є коміти, яких немає у вас, і Git не дозволяє їх перезаписати. Як уникнути: виконайте git pull, за потреби розв’яжіть конфлікти, а потім повторіть git push. Не використовуйте --force лише для того, щоб «пройшло», — так ви знищите чужі коміти.

      Джерело: Pro Git, 2.5 — Working with Remotes; Pro Git, 3.5 — Remote Branches; git-pull — Reference; GitHub Docs — About remote repositories

      9Pull Request як процес на GitHub

      Проблема. Якщо кожен у команді зливає свої гілки в main напряму, помилки потрапляють в основну версію без жодної перевірки, а обговорення змін розпорошується по месенджерах.

      Чому так. Pull Request (PR) — це не команда Git, а можливість GitHub: пропозиція злити зміни з однієї гілки в іншу. PR показує різницю між гілками, дає змогу коментувати конкретні рядки, запитувати рев’ю і бачити, чи пройшли автоматичні перевірки. Тобто це місце, де зміни обговорюють до того, як вони стануть частиною основної гілки.

      Рішення. Типовий процес такий. Ви створюєте гілку для задачі, робите в ній коміти й надсилаєте її на GitHub командою git push -u origin <гілка>. На GitHub відкриваєте Pull Request з вашої гілки в main, описуєте, що й навіщо змінено. Колеги переглядають код і залишають коментарі. Ви виправляєте зауваження новими комітами в ту саму гілку — вони автоматично з’являються в PR. Коли рев’ю пройдено, PR зливають на GitHub, після чого локально оновлюєте main і видаляєте гілку.

      switch -cгілка задачі
      ›
      commitзміни
      ›
      push -uгілка на GitHub
      ›
      Pull Requestопис, рев’ю
      ›
      Mergeна GitHub
      ›
      pullоновити main

      Коли застосовувати. Для будь-якої зміни в спільному репозиторії. Навіть у навчальних проєктах PR — найзручніший спосіб показати роботу викладачеві або ментору й отримати коментарі до конкретних рядків.

      Порада

      Один PR — одна задача. Невеликий PR з чітким описом переглядають швидко і уважно, а PR на тисячу рядків «про все» зазвичай переглядають поверхово.

      Джерело: GitHub Docs — About pull requests; GitHub Docs — Creating a pull request; GitHub Docs — GitHub flow

      10Типові помилки та як їх уникнути

      Частину помилок ми вже розібрали в розділах. Тут зібрано ті, що трапляються найчастіше, — з поясненням, чому Git поводиться саме так.

      «Я ж зробив add, чому зміни не в коміті?»

      Файл змінили після git add. Чому: індекс зберігає знімок файлу на момент add, а не посилання на файл. Як уникнути: перед комітом дивіться git status -s; MM означає, що частина правок не підготовлена.

      Секрети в репозиторії

      Файл .env з паролем закомітили, а потім додали в .gitignore. Чому це не допомагає: .gitignore не діє на вже відстежувані файли, а пароль залишається в історії, навіть якщо файл видалити наступним комітом. Як уникнути: додавайте такі файли в .gitignore до першого коміту; якщо секрет уже опубліковано, його треба вважати скомпрометованим і змінити.

      Робота прямо в main

      Усі зміни робляться в main і одразу надсилаються. Чому це погано: немає нагоди переглянути код, а недороблена робота стає частиною основної версії. Як уникнути: кожна задача — окрема гілка і Pull Request.

      Невиразні повідомлення комітів

      fix, update, asdf. Чому це погано: історія перестає бути документацією, і через місяць ніхто не знайде, де саме з’явилася зміна. Як уникнути: одне речення про суть зміни в наказовому способі.

      Плутанина між git pull і Pull Request

      Схожі назви, різні речі: git pull — команда, що забирає зміни з сервера у вашу гілку; Pull Request — запит на GitHub злити вашу гілку в чужу. Як запам’ятати: PR — це прохання до команди «підтягніть мої зміни».

      Джерело: Pro Git, 2.2 — Recording Changes to the Repository; gitignore — Notes; GitHub Docs — GitHub flow

      11Міні-задача: від порожньої теки до GitHub

      Умова. У теці todo-app лежать два файли: index.html і службовий debug.log. Репозиторію ще немає. Виконайте весь цикл:

      Ініціалізуйте репозиторій і зробіть так, щоб жоден .log-файл ніколи не потрапив в історію. Зробіть перший коміт Initial commit, у якому будуть лише index.html і .gitignore. Створіть гілку feature/footer, додайте в ній файл footer.html і закомітьте як Add footer. Поверніться в main, допишіть рядок у index.html і закомітьте як Update title. Злийте feature/footer у main і видаліть гілку. Нарешті підключіть порожній репозиторій GitHub як origin і надішліть main так, щоб надалі вистачало команди git push.

      Перевірка: такі команди мають вивести рівно це.

      Підказка

      Почніть із .gitignore і перевірте git status -s: debug.log не повинен там з’явитися. Подумайте, чому злиття в цій задачі не буде fast-forward і чому в історії з’явиться окремий коміт злиття. Для зв’язку main з origin/main згадайте прапорець команди git push.

      Пояснення. Файл .gitignore з одним рядком *.log створюємо до першого git add, тому debug.log ніколи не потрапляє навіть у статус: перший git status -s показує лише ?? .gitignore і ?? index.html. Після цього git add . безпечний.

      Гілку створюємо від першого коміту, і в ній з’являється Add footer. Повернувшись у main, ми робимо ще один коміт Update title — історія розходиться, тому злиття вже не може бути fast-forward: Git створює коміт злиття з повідомленням Merge branch 'feature/footer', у якого два батьки. Саме це видно в графі git log --graph. Після злиття гілка feature/footer більше не потрібна, і git branch -d видаляє її без втрат, бо всі її коміти вже є в main.

      Наостанок git remote add реєструє GitHub-репозиторій під іменем origin, а git push -u origin main надсилає гілку й запам’ятовує, що main відстежує origin/main. Тому git status -sb показує ## main...origin/main без ahead чи behind — локальна й віддалена історії збігаються.

      12Квіз: 10 питань

      Оберіть одну відповідь у кожному питанні. Якщо перша спроба не влучна, ви отримаєте навідне запитання і зможете спробувати ще раз, але в підсумковий бал зараховується лише перша відповідь.
