Потік виконання програми

Досі наші програми виконувалися як рецепт без жодних «якщо»: перший рядок, другий, третій — і кінець. Такий порядок називають лінійним потоком виконання (linear program flow). Потік виконання (program flow) — це послідовність, у якій комп'ютер виконує інструкції програми. Він визначає, яка частина коду спрацює, у якому порядку і чи спрацює взагалі.

Справжні задачі рідко бувають лінійними. Банкомат видає гроші, лише якщо на рахунку достатньо коштів. Інтернет-магазин нараховує знижку, лише якщо сума замовлення перевищує поріг. Програма має вміти вибирати один із кількох шляхів залежно від даних, і тоді потік стає нелінійним: виконання розгалужується. За це відповідають керувальні конструкції (control structures). Їх дві великі групи: умовні конструкції, які вибирають, який блок виконати (цей модуль), і цикли, які повторюють блок кілька разів (модуль 05).

flowchart TD
    A[Початкові значення] --> B{Умова істинна?}
    B -- так --> C[Виконати один блок]
    B -- ні --> D[Виконати інший блок]
    C --> E[Наступна інструкція]
    D --> E

Будь-яке розгалуження спирається на умову — вираз, який дає true або false. Щоб такі умови будувати, спершу треба добре розуміти оператори: як Java обчислює арифметику, як змінює змінні на одиницю, як порівнює значення і як поєднує кілька умов. З цього і почнемо.

Оператори присвоєння та арифметичні оператори

Оператор присвоєння = записує значення праворуч у змінну ліворуч. Це не «дорівнює» з математики: запис x = x + 1 для математика безглуздий, а для Java означає «обчисли x + 1 і поклади результат назад у x». Порівняння на рівність у Java пишеться інакше — ==, і ця різниця нам ще знадобиться.

Арифметичні оператори (arithmetic operators) працюють так само, як в алгебрі: + додавання, - віднімання, * множення, / ділення, % остача від ділення. Пріоритет теж звичний: множення, ділення й остача виконуються раніше за додавання й віднімання, а дужки змінюють порядок.

Два останні рядки найцікавіші. Коли обидва операнди цілі, / виконує цілочисельне ділення: дробова частина просто відкидається, без округлення. 11 / 7 — це 1,57…, але Java залишає лише 1. Остача % відповідає на запитання «скільки залишилося після цілочисельного ділення»: 11 = 7 · 1 + 4, тому 11 % 7 дорівнює 4.

Проблема

Студент рахує середній бал як int поділене на int і отримує «зрізаний» результат, наприклад 1 замість 1.57.

Чому так стається

Тип результату визначається типами операндів, а не типом змінної, у яку його потім записують. Якщо обидва операнди int, Java виконує цілочисельне ділення ще до того, як результат кудись потрапить. Навіть double avg = 11 / 7; дасть 1.0: спершу обчислюється 1, а вже потім воно перетворюється на double.

Рішення

Зробіть хоча б один операнд дробовим: 11 / 7.0 дає 1.5714285714285714. Тоді Java виконує ділення з плаваючою комою.

Коли застосовувати

Щоразу, коли ділите цілі числа і вам потрібна дробова частина: середнє значення, відсоток, частка. Якщо ж потрібна саме ціла частина (скільки повних коробок по 7 штук вийде з 11 товарів), цілочисельне ділення — саме те, що треба.

Остача від ділення здається дрібницею, але в умовних конструкціях вона трапляється постійно: число парне, якщо остача від ділення на 2 дорівнює нулю, кратне трьом, якщо n % 3 == 0, і так далі. Тут є одна важлива деталь: знак остачі в Java збігається зі знаком діленого (лівого операнда).

Що виведе програма?

Вивід
-4
4

Java ділить так, що ціла частина частки округлюється до нуля, а остача «забирає» знак діленого. −11 = 7 · (−1) + (−4), тому -11 % 7 дорівнює -4. Для 11 % -7 ділене додатне, тому й остача додатна: 4. Звідси наслідок, який ми використаємо в практичній задачі: для від'ємного непарного числа n % 2 дає -1, а не 1.

Оператор + має ще одну роль: якщо хоча б один операнд — рядок, він виконує конкатенацію (string concatenation), тобто склеювання рядків. Вирази обчислюються зліва направо, і саме це породжує класичну пастку.

Що виведе програма?

Вивід
Сума: 12
3 — сума
Сума: 3

У першому рядку Java спершу склеює "Сума: " і 1, отримує рядок "Сума: 1", а потім склеює його з 2. Числа так і не додаються. У другому рядку зліва стоять два числа, тому 1 + 2 дає 3, і лише потім до результату дописується рядок. У третьому дужки змушують обчислити суму раніше. Правило просте: якщо в рядку з текстом треба щось порахувати, беріть обчислення в дужки.

У Java є й складені оператори присвоєння (compound assignment): x += 5 означає те саме, що x = x + 5, а x -= 2, x *= 3, x /= 4, x %= 2 працюють аналогічно. Вони просто коротші й часто трапляються в чужому коді.

Унарні оператори

Унарні оператори (unary operators) мають лише один операнд. Унарний плюс + позначає додатне значення і майже ніколи не пишеться явно. Унарний мінус - змінює знак виразу: якщо x дорівнює 5, то -x дорівнює -5. Оператор логічного заперечення ! (logical complement) перевертає значення типу boolean: !true — це false. Найбільше запитань викликають інкремент ++ (збільшення на 1) і декремент -- (зменшення на 1).

Кожен із них має дві форми. Префіксна (++x) спершу змінює змінну, а потім віддає у вираз нове значення. Постфіксна (x++) спершу запам'ятовує старе значення, віддає його у вираз, а потім змінює змінну. Якщо інкремент стоїть окремим рядком (x++;), різниці між формами немає: результат виразу ніхто не використовує, і в обох випадках змінна просто збільшується. Різниця проявляється лише тоді, коли інкремент — частина більшого виразу.

У рядку a = x++ змінна a отримала старе значення 5, а x уже після цього став 6. У рядку b = ++x спершу x збільшився з 5 до 6, і саме нове значення потрапило в b.

Що виведе програма?

Продовжимо попередній приклад: після всіх рядків x дорівнює 7. Що буде в a та x після такого рядка?

Вивід
a=36 x=11

Java обчислює доданки строго зліва направо, і кожен інкремент одразу змінює x для наступних доданків:

  1. x++ віддає 7, після чого x стає 8.
  2. ++x спершу робить x рівним 9 і віддає 9.
  3. ++x робить x рівним 10 і віддає 10.
  4. x++ віддає 10, після чого x стає 11.

Сума: 7 + 9 + 10 + 10 = 36. Такий код корисний як вправа на розуміння префіксної та постфіксної форм, але в робочій програмі його писати не варто: одна змінна змінюється чотири рази в одному виразі, і читач мусить проганяти його вручну.

Оператори порівняння

Оператори порівняння (equality and relational operators) порівнюють два значення і завжди повертають boolean: true або false. Ось вони: == дорівнює, != не дорівнює, > більше, >= більше або дорівнює, < менше, <= менше або дорівнює. Саме результат порівняння стає умовою в if, тому вираз на кшталт x >= y можна сприймати як твердження, яке буває істинним або хибним.

Результат порівняння можна зберегти у змінну типу boolean, наприклад boolean isAdult = age >= 18;, і потім використовувати її в умові. Добра назва такої змінної робить умову читабельною майже як речення.

Порівняння дробових чисел через ==

Числа double зберігаються у двійковому вигляді, і більшість десяткових дробів записати так точно неможливо. Тому 0.1 + 0.2 == 0.3 дає false: насправді сума дорівнює 0.30000000000000004. Для дробових результатів обчислень порівняння через == ненадійне. Безпечніше перевіряти, що різниця між числами менша за невеликий допуск, або порівнювати через < і >. Цілі числа (int, long) порівнюються через == точно.

Логічні оператори

Часто одного порівняння замало: оцінка має бути від 3 до 5 включно, день — субота або неділя. Для поєднання умов є логічні оператори. Оператор && (умовне І, conditional-AND) дає true, лише якщо обидві частини істинні. Оператор || (умовне АБО, conditional-OR) дає true, якщо істинна хоча б одна частина. Оператор ! (логічне НЕ) перевертає значення.

Цей вираз перевіряє, що score лежить у діапазоні від 3 до 5. Зверніть увагу: в Java не можна написати 3 <= score <= 5, як у математиці. Вираз 3 <= score дає boolean, а порівнювати boolean з числом через <= не можна, тому компілятор його не пропустить.

Пріоритет: && сильніший за ||

Коли в одному виразі є і &&, і ||, Java спершу обчислює &&, так само як множення виконується раніше за додавання. Без дужок це легко прочитати неправильно.

Що виведе програма?

Вивід
true
true
false

Спершу обчислимо всі порівняння: t > s — це 5 > 4, тобто true; t > v — 5 > 7, false; s < v — 4 < 7, true; s > v — 4 > 7, false.

У першому рядку && виконується першим: true && false дає false, а потім false || true дає true.

У другому рядку && теж виконується першим, тобто вираз читається як true || (false && false). Права частина — false, але true || false все одно true.

У третьому рядку дужки змінюють порядок: спершу (true || false) дає true, потім true && false дає false. Порівняння другого і третього рядків показує, що однакові порівняння з різним групуванням дають різний результат.

Коротке замикання: різниця між && і &

У Java є ще оператори & і |. Для операндів типу boolean вони дають той самий логічний результат, що й && та ||, але обчислюють вираз інакше. Оператори && і || працюють за принципом короткого замикання (short-circuit evaluation): якщо результат зрозумілий уже з лівої частини, права взагалі не обчислюється. Для && це трапляється, коли ліва частина false (тоді все одно буде false), а для || — коли ліва частина true. Оператори & і | завжди обчислюють обидві частини.

Поки права частина — просте порівняння, різниця непомітна. Вона стає видимою, коли права частина щось змінює. У прикладах нижче всередині умови стоїть присвоєння (b = 72): воно записує в b значення 72 і саме дорівнює 72.

Що виведе програма?

Вивід
Variable 'a' = 37
Variable 'b' = 24

a > 50 — це 37 > 50, тобто false. Для && цього достатньо: результат буде false незалежно від правої частини, тому Java її пропускає. Присвоєння b = 72 так і не виконується, і b залишається 24.

Що виведе програма?

Той самий код, але з & замість &&:

Вивід
Variable 'a' = 37
Variable 'b' = 72

Оператор & обчислює обидві частини завжди. Ліва дає false, але права все одно виконується: b отримує 72, а 72 < 50 дає false. Умова хибна, тому «Do something...» не друкується, але побічний ефект уже стався.

З || і | ситуація дзеркальна: коротке замикання спрацьовує, коли ліва частина true.

Що виведе програма?

Вивід
Do something...
Variable 'a' = 57
Variable 'b' = 24

57 > 50 дає true, а для || цього достатньо, щоб уся умова була true. Права частина пропускається, тому b не змінюється. Якщо замінити || на |, вивід буде Do something..., Variable 'a' = 57, Variable 'b' = 72: умова та сама, але присвоєння в правій частині виконається.

Проблема

Права частина умови може бути небезпечною, якщо ліва не виконалась. Наприклад, ділити на c можна лише тоді, коли c не нуль.

Чому так стається

Коротке замикання гарантує порядок: права частина && виконується тільки тоді, коли ліва вже дала true. Тому ліву частину можна використати як «охоронця» для правої. З & такої гарантії немає: if (c != 0 & 10 / c > 1) при c = 0 завершує програму з ArithmeticException: / by zero, бо ділення виконується попри хибну ліву частину.

Рішення

Пишіть охоронну перевірку зліва і використовуйте &&: if (c != 0 && 10 / c > 1). При c = 0 ділення просто не відбувається.

Коли застосовувати

У звичайних умовах завжди використовуйте && і ||. Оператори & і | для boolean потрібні дуже рідко — лише тоді, коли обидві частини свідомо мають виконатися. А присвоєння всередині умови, як у прикладах вище, — це прийом для демонстрації механізму, а не для робочого коду: такий побічний ефект легко не помітити при читанні.

Термінологія

На слайдах & і | згруповані з && і || під назвою «Conditional-AND / Conditional-OR». У специфікації мови Java (JLS) умовними (conditional) називаються лише && і ||, а &, | для boolean — це логічні оператори (boolean logical operators) без короткого замикання. Для цілих чисел & і | працюють ще й як побітові оператори, але це окрема тема, яка в цьому курсі не потрібна.

Правила оформлення коду

Компілятору байдуже, як розставлені відступи та дужки. Але код читають люди: ви через тиждень, колега на код-рев'ю, викладач. Тому в Java є загальноприйняті угоди про оформлення коду (code conventions), і більшість із них стосується саме умовних конструкцій, бо там помилки оформлення найчастіше перетворюються на логічні помилки.

Фігурні дужки та пробіли

Між назвою методу і відкривною дужкою ( пробілу немає: emptyMethod(), а не emptyMethod (). Відкривна фігурна дужка { стоїть у кінці того самого рядка, що й оголошення класу, методу чи if. Закривна } стоїть в окремому рядку з тим самим відступом, що й рядок, який відкрив блок. Після коми в списку параметрів чи аргументів ставиться пробіл: Sample(int i, int j), а не Sample(int i,int j).

Чому на слайді написано `class Sample extends Object`

Кожен клас у Java автоматично успадковується від класу Object, навіть якщо ви цього не пишете. Запис extends Object лише робить це явним, і на практиці його не пишуть. Що таке успадкування і extends, детально розберемо в модулі 07. Для цього модуля важливо одне: саме від Object усі класи отримують методи equals() і hashCode(), про які йтиметься в кінці конспекту.

Не ховайте поле за локальною змінною

Ще одна угода зі слайда: не оголошуйте локальну змінну з тим самим ім'ям, що й поле класу. Таке оголошення затіняє (shadows) поле: всередині методу ім'я тепер посилається на локальну змінну, а поле залишається недоторканим.

Антипатерн: Локальна змінна з ім'ям поля

Через слово int у конструкторі рядок int value = start; створює нову локальну змінну, яка зникає, щойно конструктор завершується. Поле value ніхто не змінював, тому воно зберігає значення за замовчуванням 0. Код компілюється без помилок, і проблема проявляється лише в неправильному результаті.

Як правильно

Без оголошення типу рядок присвоює значення саме полю. Відомий з модуля 03 запис this.value = value; у конструкторі з параметром value теж працює правильно: там this. явно вказує на поле, тому це прийнятий у Java шаблон, а не порушення.

Магічні числа

Числові літерали не варто вписувати в код напряму. Якщо в умові стоїть if (mark > 3), читач мусить здогадуватися, що таке 3. Ключове слово final забороняє змінювати значення після ініціалізації, а static робить константу спільною для всього класу; назву константи за угодою пишуть великими літерами через підкреслення. Додатковий виграш: якщо прохідний бал зміниться, його доведеться виправити в одному місці.

Виняток становлять -1, 0 і 1: їх можна писати напряму, наприклад як початкове значення лічильника. На слайді цей виняток пояснено на прикладі лічильника циклу for, а цикли ми розберемо в модулі 05.

Інструкція if

Інструкція if перевіряє умову і виконує блок коду лише тоді, коли умова дорівнює true. Якщо умова false, блок пропускається, і програма продовжує з першої інструкції після нього.

Умова в дужках обов'язково має тип boolean. Це може бути порівняння, логічний вираз, змінна типу boolean або виклик методу, що повертає boolean.

Метод passMessage спершу готує відповідь «за замовчуванням», а if замінює її, лише якщо оцінка вища за прохідну. Метод повертає рядок, а друкує його main: так логіку можна перевірити на будь-яких оцінках, не змінюючи сам метод.

Антипатерн: if без фігурних дужок

Без фігурних дужок if керує лише однією наступною інструкцією. Відступ другого рядка створює ілюзію, що він теж усередині if, але Java відступів не читає: друге повідомлення друкується завжди. Найчастіше така помилка з'являється, коли до if з одним рядком пізніше дописують другий.

Як правильно

З фігурними дужками межі блоку видно явно, і додавання нового рядка нічого не ламає. Тому угода вимагає дужок навіть для блоку з однієї інструкції.

Антипатерн: Присвоєння замість порівняння

Один знак = — це присвоєння. Вираз isActive = true записує true у змінну і сам дорівнює true, тому умова виконується завжди, а значення змінної непомітно зіпсоване. З числами Java таку помилку ловить: if (n = 5) не компілюється з повідомленням incompatible types: int cannot be converted to boolean. Але для змінних типу boolean код компілюється.

Як правильно

Змінна типу boolean уже є умовою, порівнювати її з true не потрібно. Для заперечення пишуть if (!isActive), а не if (isActive == false).

Інструкція if-else

Часто треба не просто пропустити блок, а виконати альтернативний. Для цього до if додають гілку else: вона виконується тоді, коли умова хибна. З двох гілок завжди виконується рівно одна.

Зверніть увагу, що обидві гілки містять return. Java перевіряє, що метод із типом результату String повертає значення на будь-якому шляху виконання. Якби else не було, компілятор повідомив би про помилку missing return statement: для теплої погоди метод нічого б не повернув.

Ланцюжок if-else-if

Коли варіантів більше двох, гілку else можна відразу продовжити новою перевіркою if. Такий ланцюжок (else-if ladder) перевіряє умови по черзі зверху вниз і виконує блок першої істинної умови. Решта умов після цього вже не перевіряються. Якщо жодна умова не виконалась, спрацьовує завершальний else, якщо він є.

flowchart TD
    A{"score >= 90?"} -- так --> R1[A]
    A -- ні --> B{"score >= 75?"}
    B -- так --> R2[B]
    B -- ні --> C{"score >= 60?"}
    C -- так --> R3[C]
    C -- ні --> R4[F]

Для 74 перша умова хибна, друга теж (74 менше за 75), третя істинна — результат C. Умові score >= 60 не потрібна перевірка «і менше за 75»: якщо виконання дійшло до неї, значить, усі попередні умови вже виявились хибними. Саме тому порядок умов у ланцюжку має значення.

Антипатерн: Неправильний порядок умов

Для gradeFor(95) цей метод повертає C. Число 95 задовольняє першу ж умову score >= 60, тому ланцюжок зупиняється на ній, а гілки для B і A стають недосяжними: будь-яке число, більше або рівне 75, уже «перехоплене» першою перевіркою. Компілятор такої помилки не бачить.

Як правильно

Розташовуйте умови від найвужчої до найширшої: спершу >= 90, потім >= 75, потім >= 60, як у прикладі Grades вище. Корисна самоперевірка: для кожної гілки придумайте значення, яке має потрапити саме в неї, і переконайтеся, що жодна умова вище його не перехопить.

Ланцюжок if-else-if — універсальний інструмент: умови в ньому можуть бути будь-якими, з діапазонами, кількома змінними, викликами методів. Якщо ж вибір робиться за конкретним значенням однієї змінної (номер дня, код команди, текстова відповідь), зручніший switch, до якого ми перейдемо після тернарного оператора.

Тернарний оператор

Тернарний оператор ?: (ternary operator, його ще називають умовним оператором) — це коротка форма if-else для випадку, коли треба вибрати одне з двох значень. Він називається тернарним, бо має три операнди: умову, значення для true і значення для false.

На відміну від if, тернарний оператор — це вираз: він обчислюється в значення, яке можна присвоїти, повернути з методу або передати в println. Наприклад, метод weatherAdvice з попереднього розділу можна записати одним рядком:

Що виведе програма?

Які значення отримають str1 і str2?

Вивід
str1 = yes, s = 5
str2 = no, a = 2

У першому виразі префіксний ++s спершу збільшує s до 5 і віддає 5. Умова 5 >= 5 істинна, тому str1 дорівнює "yes".

У другому виразі постфіксний a-- віддає в порівняння старе значення 3, а вже потім зменшує a до 2. Умова 3 == 2 хибна, тому str2 дорівнює "no". Цікаво, що після виконання рядка a справді дорівнює b, але порівнювалось ще старе значення. Дужки навколо умови в другому рядку не обов'язкові, бо порівняння має вищий пріоритет за ?:, проте з ними код читається легше.

Інструкція switch

Інструкція switch вибирає один із кількох блоків коду за значенням виразу. Вираз у дужках обчислюється один раз, після чого його значення по черзі порівнюється з мітками case. Якщо збіг знайдено, виконання переходить до відповідної мітки. Якщо жодна мітка не підійшла, виконується блок default, якщо він є.

Важливо розуміти, що case — це саме мітка, точка входу, а не окремий блок. Знайшовши збіг, Java починає виконувати інструкції з цієї мітки і йде вниз, доки не зустріне break або кінець switch. Це явище називають проходженням крізь мітки (fall-through). Ключове слово break перериває switch і передає керування першій інструкції після нього.

Що виведе програма?

Вивід
ABC
DEF

Значення "ABC" збігається з першою міткою, тому друкується ABC. Після цього немає break, і виконання «провалюється» далі: інструкції під міткою "DEF" теж виконуються, хоча input зовсім не дорівнює "DEF". Лише break у кінці цього блоку зупиняє switch, тому Default не друкується. Коментар // fall through — добра практика: він повідомляє читачеві, що відсутність break навмисна, а не забута.

Забутий break — одна з найчастіших помилок у класичному switch. Проте fall-through буває й корисним: кілька міток поспіль без інструкцій між ними ведуть до одного спільного блоку. Так зручно обробляти кілька значень однаково.

Для введення YES програма друкує:

Вивід
Do you enjoy Java? (yes/no/maybe)
Great!

Виклик toLowerCase() перетворює відповідь на малі літери, тому YES, Yes і yes обробляються однаково. Мітка "yes" не має власних інструкцій, тож виконання переходить до інструкцій під "maybe". Для no програма друкує Too bad!, для будь-якого іншого тексту — Wrong!. Змінна result оголошена без значення, але компілятор приймає return result, бо бачить, що кожна гілка, включно з default, її заповнює. Без default такий код не скомпілювався б.

Які типи можна використовувати в switch

Вираз у switch має бути одного з типів byte, short, char, int, відповідного класу-обгортки (Byte, Short, Character, Integer) або String (з Java 7). Підтримуються також переліки enum, які ми розглянемо в модулі 06. Типи long, float, double і boolean у класичному switch не дозволені: switch по змінній типу long не компілюється з повідомленням selector type long is not allowed. Для діапазонів і дробових чисел використовуйте if-else-if.

Значення в мітках case мають бути константами, відомими під час компіляції (літерали на кшталт 3 чи "yes" або константи static final), і не можуть повторюватися в одному switch.

switch і null

Якщо змінна типу String дорівнює null, класичний switch по ній завершує програму з NullPointerException, і default тут не допомагає. Перевіряйте рядок на null до switch, якщо він може бути порожнім посиланням.

Слайд описує порівняння значення з мітками як порівняння через ==. Для чисел і символів це так. Для рядків — ні: switch по String порівнює вміст рядків, тобто працює як equals(), а не як ==. Це видно навіть з тексту помилки для null: Cannot invoke "String.hashCode()". Щоб швидко знайти потрібну мітку, Java спершу обчислює хеш-код рядка (про hashCode() йтиметься в кінці конспекту), а потім перевіряє збіг через equals(). Чим == відрізняється від equals() і чому для рядків це критично, розберемо в розділі про порівняння об'єктів.

switch-вираз

Класичний switch має дві слабкі сторони: забутий break тихо ламає логіку, а щоб отримати значення, доводиться оголошувати змінну заздалегідь і присвоювати її в кожній гілці. Обидві проблеми розв'язує нова форма — мітки зі стрілкою case ... -> і switch-вираз (switch expression).

У формі зі стрілкою fall-through немає: виконується лише права частина знайденої мітки, і break не потрібен. Кілька значень, що обробляються однаково, перелічуються через кому в одній мітці. Проблема

Що станеться, якщо значення не підійде під жодну мітку switch-виразу?

Чому так стається

Вираз мусить мати значення завжди, інакше змінній, якій його присвоюють, не було б що отримати. Тому switch-вираз має бути вичерпним (exhaustive): його мітки мають покривати всі можливі значення. Для int чи String можливих значень незліченно багато, і без default код не компілюється з повідомленням the switch expression does not cover all possible input values.

Рішення

Для int, char і String у switch-виразі завжди потрібна гілка default. Компілятор перевіряє це сам, тож забути про «непередбачений» випадок не вийде.

Коли застосовувати

Щоразу, коли switch обчислює значення за ключем: назва дня за номером, ціна за кодом тарифу, відповідь за командою. Класичний switch з двокрапками сьогодні потрібен рідко, але трапляється в старому коді, тому його механіку треба розуміти.

yield: значення з блоку

Права частина стрілки може бути простим виразом, як "Great!", або блоком у фігурних дужках, якщо перед результатом треба виконати кілька дій. Але блок сам по собі не є значенням, тож Java має дізнатися, що саме з нього повернути. Для цього є ключове слово yield: воно завершує блок і віддає значення як результат усього switch-виразу.

Для першої зони вартість фіксована, і вистачає простого виразу. Для другої вона обчислюється в кілька кроків, тому потрібен блок і yield. Значення -1.0 для невідомої зони — тимчасова домовленість «такої зони немає»; правильніший спосіб повідомити про некоректні дані — винятки, які розглядаються в модулі 09.

Чому не return? Тому що return завершив би весь метод, а yield завершує лише switch-вираз і повертає значення саме йому. Якщо в блоці забути yield, код не скомпілюється з повідомленням switch rule completes without providing a value.

Що виведе програма?

Програма зі слайда. Що вона надрукує для введення admin, а що — для guest?

Для admin:

Вивід
Assigning full access
Permissions: ALL_PERMISSIONS

Для guest:

Вивід
Permissions: NO_ACCESS

Введений рядок admin перетворюється на ADMIN і потрапляє в першу гілку. Блок спершу друкує повідомлення, потім yield віддає "ALL_PERMISSIONS" у змінну permissions, і лише після цього виконується останній println. Для guest жодна мітка не підходить, тому спрацьовує default з простим виразом без блоку і без додаткового виводу.

yield можна використовувати й у switch-виразі з класичними мітками-двокрапками: case "a": yield 1;. Але на практиці майже завжди пишуть форму зі стрілками.

Версії Java

На слайді сказано, що switch-вирази з'явились у Java 14 як preview і стали офіційними в Java 17. Насправді вони були preview-можливістю в Java 12 і 13 і стали стандартною частиною мови в Java 14 (JEP 361). У Java 21 до switch додали зіставлення зі зразком (pattern matching for switch, JEP 441), яке дозволяє вибирати гілку за типом об'єкта; воно стане зрозумілим після тем про успадкування та інтерфейси (модулі 07–08). У поточній LTS-версії Java 25 підтримка примітивних типів у шаблонах, зокрема switch по long, double чи boolean, усе ще є preview-можливістю (JEP 507) і без спеціальних прапорців компілятора недоступна. Усе, що описано в цьому конспекті, однаково працює в Java 17, 21 і 25.

Порівняння об'єктів

Досі ми порівнювали числа, і == працював бездоганно. З об'єктами все інакше. Змінна примітивного типу (int, double, boolean) зберігає саме значення. Змінна типу класу (String, Student) зберігає посилання (reference) на об'єкт, тобто вказівку, де цей об'єкт лежить у пам'яті. Тому для об'єктів є два різні запитання: «чи це той самий об'єкт» і «чи це однакові за вмістом об'єкти».

Візьмемо клас зі слайда (гетери та сетери, що були на слайді, тут не впливають на результат, тому опущені).

Кожен виклик new створює окремий об'єкт у пам'яті. Оператор == для об'єктів порівнює посилання, тобто перевіряє, чи це той самий об'єкт. student1 і student2 — два різні об'єкти з однаковими даними, тому == дає false. А student3 = student1 не створює нового об'єкта: обидві змінні вказують на один, тому student1 == student3 дає true.

Несподіваний другий рядок: equals() теж дав false. Метод equals() наш клас отримав від Object, і там він реалізований так само, як ==: об'єкт дорівнює лише самому собі. Щоб equals() порівнював вміст, його треба перевизначити.

Рядки порівнюють через equals

Найважливіший практичний наслідок стосується рядків. String — це клас, тому == для рядків порівнює посилання, а не текст. Клас String уже має власний equals(), який порівнює символи.

Підступність у тому, що порівняння двох літералів через == часто дає true: Java зберігає однакові рядкові літерали в одному екземплярі (string pool), і String literal = "yes"; literal == "yes" справді друкує true. Код, перевірений на літералах, працює, а на даних від користувача — ні. Приклад зі слайда day == "Saturday" || day == "Sunday" має саме цю ваду.

Як правильно

Рядки завжди порівнюйте через equals(). Якщо змінна може бути null, пишіть літерал зліва: "yes".equals(answer) безпечно повертає false для null, тоді як answer.equals("yes") для null завершиться NullPointerException.

Перевизначення equals

Щоб Student порівнювався за іменем і віком, у клас додають власну версію методу equals(). Заміну успадкованого методу своєю реалізацією називають перевизначенням (overriding). Докладно механізм перевизначення ми розберемо в модулі 07, а зараз зосередимось на тому, що робить кожен рядок.

Анотація @Override повідомляє компілятору, що метод має замінити успадкований. Сигнатура мусить точно збігатися з тією, що в Object: public boolean equals(Object o), параметр саме типу Object, бо порівнювати можна з будь-яким об'єктом.

Метод побудований як ланцюжок перевірок від найдешевших до найдорожчих, і кожна відсікає свій випадок. Перша, this == o, повертає true, якщо об'єкт порівнюють сам із собою: тоді далі перевіряти нічого. Друга відкидає null і об'єкти іншого класу: getClass() повертає клас об'єкта, і студент не може дорівнювати, скажімо, рядку. Тут знову працює коротке замикання: якщо o == null, права частина o.getClass() не виконується, тож NullPointerException не виникне. Третій рядок, (Student) o, — це приведення типу (cast): ми вже переконались, що o справді Student, і тепер кажемо про це компілятору, щоб отримати доступ до полів age і name. Нарешті, порівнюються поля: число через !=, рядок через equals().

Антипатерн: equals з параметром типу Student

Здається логічним приймати одразу Student, але це вже інший метод з іншою сигнатурою, а не заміна успадкованого. Без @Override такий код компілюється, і в деяких викликах успадкований equals(Object) продовжує працювати по-старому. Саме тут @Override рятує: з ним компілятор повідомляє method does not override or implement a method from a supertype.

Як правильно

Параметр завжди типу Object, а перевірка класу і приведення типу — всередині методу, як у прикладі вище. Завжди ставте @Override: ця анотація перетворює непомітну логічну помилку на помилку компіляції.

Метод equals() має виконувати контракт, описаний у документації класу Object. Він має бути рефлексивним (x.equals(x) завжди true), симетричним (якщо x.equals(y), то й y.equals(x)), транзитивним (якщо x дорівнює y, а y дорівнює z, то x дорівнює z), узгодженим (повторні виклики для незмінених об'єктів дають той самий результат), а x.equals(null) для будь-якого непорожнього x має повертати false. Шаблон зі слайда виконує всі ці вимоги, тому його і варто використовувати.

hashCode

Метод hashCode() теж визначений у класі Object як public int hashCode() і повертає ціле число — хеш-код об'єкта. Хеш-код — це «відбиток» об'єкта, обчислений з його стану. Його використовують хеш-структури даних (хеш-таблиці, хеш-множини), щоб не порівнювати шуканий об'єкт з усіма підряд: спершу за хеш-кодом визначається, де об'єкт може лежати, і лише потім equals() перевіряє точний збіг. Саме так працює switch по рядку, який ми бачили вище.

Головне правило контракту: якщо два об'єкти рівні за equals(), їхні хеш-коди мають бути однаковими. Зворотне не обов'язкове: різні об'єкти можуть випадково мати однаковий хеш-код. Звідси практичне правило: перевизначили equals() — обов'язково перевизначте й hashCode(), використовуючи ті самі поля.

Метод бере хеш-код імені (у String він уже правильно реалізований) і «домішує» до нього вік. Множник 31 — звичне непарне просте число; той самий множник використовує й сам String для обчислення свого хеш-коду. Множення перед додаванням потрібне, щоб внесок кожного поля впливав на результат по-різному.

Тепер повна версія класу:

== як і раніше дає false: об'єктів два, і перевизначення equals() цього не змінює. А equals() тепер порівнює вміст: однакові ім'я та вік дають true, інший вік — false, null — false. Рівні об'єкти мають однаковий хеш-код, тобто контракт виконано.

Антипатерн: equals без hashCode

Якщо перевизначити лише equals(), то для двох студентів «Anna, 25» equals() поверне true, а hashCode() майже напевно поверне різні числа, бо успадкована реалізація з Object нічого не знає про поля. Компілятор цього не помітить, і на простих порівняннях програма поводитиметься правильно. Проблема проявиться пізніше, у хеш-колекціях: об'єкт, рівний тому, що вже лежить у колекції, не буде знайдений, бо його шукатимуть «не в тому місці».

Як правильно

Перевизначайте equals() і hashCode() завжди разом і на основі тих самих полів.

Хеш-код за замовчуванням

На слайді сказано, що за замовчуванням hashCode() обчислюється на основі адреси об'єкта в пам'яті. Документація Object такого не гарантує: вона вимагає лише, щоб значення було стабільним для незміненого об'єкта і, наскільки це практично можливо, різним для різних об'єктів. Як саме воно обчислюється, залежить від реалізації JVM, тому покладатися на зв'язок хеш-коду з адресою не можна.

Генерація в IDE і null-безпечні варіанти

Писати equals() і hashCode() вручну доводиться рідко: IntelliJ IDEA генерує обидва методи через меню Code → Generate (Alt+Insert), де достатньо вибрати поля. Зверніть увагу, що шаблон зі слайда завершиться NullPointerException, якщо name дорівнює null. Згенерований IDE код зазвичай використовує допоміжні методи Objects.equals(name, student.name) і Objects.hash(name, age) з класу java.util.Objects, які коректно обробляють null.

Попередній погляд: де equals і hashCode стануть критичними

У модулях 11–12 ви працюватимете з колекціями HashSet і HashMap. Вони зберігають об'єкти саме за хеш-кодом і перевіряють рівність через equals(). Студент без правильних equals() і hashCode() у HashSet може з'явитися двічі, а пошук «такого самого» студента в HashMap поверне null. Тому звичка завжди перевизначати обидва методи разом закладається вже зараз.

Практика

Задачі нижче відповідають практичним завданням зі слайдів. Код у розв'язках побудовано за правилом курсу: логіка в окремих методах, які повертають значення, main лише викликає їх і друкує, а Scanner створюється один раз.

Міні-задача: Скільки чисел непарні

Користувач вводить з консолі три цілі числа. Програма визначає, скільки з них непарні, і виводить результат. Для введення 3 -5 8 очікуваний результат — 2. Подумайте, як правильно перевірити непарність, щоб від'ємні числа теж рахувались.

Підказка

Винесіть перевірку одного числа в метод isOdd(int number), що повертає boolean. Згадайте, яку остачу дає -5 % 2.

Показати рішення

Три окремі if, а не ланцюжок else-if, бо кожне число перевіряється незалежно: збіг для першого не має скасовувати перевірку другого. Метод isOdd повертає результат порівняння напряму, без if: вираз number % 2 != 0 вже має тип boolean.

Ключова деталь — != 0 замість == 1. Якщо написати return number % 2 == 1;, для того самого введення 3 -5 8 програма надрукує Непарних чисел: 1: остача -5 % 2 дорівнює -1, а не 1, тому -5 не буде зарахована. Умова «остача не нуль» правильна для чисел будь-якого знаку.

Міні-задача: Найдорожчий товар і найбільший запас

Створіть клас Product з полями String name, double price і int quantity. У main створіть чотири товари: «Кавоварка» (3200.0, 5 шт.), «Чайник» (950.0, 12 шт.), «Тостер» (1400.0, 12 шт.), «Блендер» (2100.0, 7 шт.). Виведіть назву і кількість найдорожчого товару, а також назви всіх товарів з найбільшою кількістю (їх може бути кілька). Масиви й цикли ще не вивчені, тому обійдіться методами та умовами.

Підказка

Метод, що порівнює лише два товари і повертає дорожчий, можна викликати ланцюжком: переможець першої пари змагається з третім товаром, переможець — із четвертим. Для другої частини спершу знайдіть найбільшу кількість, а потім зберіть назви товарів саме з такою кількістю.

Показати рішення

Метод moreExpensive розв'язує найменшу підзадачу, а mostExpensive складає з неї розв'язок для чотирьох товарів. Порівняння строге (>), тому при однаковій ціні переможцем залишається товар, переданий першим.

У maxQuantity початкове значення max береться з першого товару, а не дорівнює нулю: так результат завжди є кількістю одного з товарів. Окремі if, а не else-if, потрібні, бо кожен товар порівнюється з поточним максимумом незалежно.

Чайник і тостер мають однакову найбільшу кількість, тому знайти «один» товар тут недостатньо, і задача розділена на два кроки. Метод addIfMatches дописує назву, лише якщо кількість збігається, і ставить кому тільки між назвами. Порожній рядок перевіряється через equals(""), а не ==, з тієї самої причини, що й у розділі про порівняння рядків. Коли ви вивчите масиви й цикли (модуль 05), цю задачу можна буде розв'язати для будь-якої кількості товарів, без повторення рядків для кожного з них.
